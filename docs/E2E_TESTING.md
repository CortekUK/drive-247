# End-to-end testing — payments (Wave 4)

**Status:** Sep 26 2026, branch `haseeb/payment-unification`. Built and tested
offline. **Nothing is applied, deployed or run against any database.** The live
runner is ready to switch on once its migration is applied and its function
deployed — each a separate approval (§7).

> "Payments are too risky for us to take your word. We'll accept evidence only."
> "However you test it, make sure I can test it that same way."
> "Put the testing in the developer tab." — spec §1, §9

This is how that is met: **one scenario list**, written once with every expected
number worked out by hand, run the same way by the automated tests and by you
in the Developer tab — and every run leaves a record you can reopen.

---

## 1. The one scenario list

`tests/e2e/scenarios/` — data, steps and hand-derived expected values. Nothing
in it computes an expected value: each amount is a literal in cents with its
arithmetic beside it (`{ cents: 30000, math: "3 × 100.00 = 300.00" }`) and in a
comment above it. The tests re-add every `math` string only to catch a typo.

The stated rates everything is derived from (`fixtures.ts`): booking **$100/day**,
extension **$100/day**, auto-extend **$350/week**, pay-as-you-go **$40/day**,
installments **3 × $200**, payment plan **$600 split 3 ways**, prepaid credit
**$350**; tax and service fee **off**.

Every live scenario **ends with a Finances tie-out**: the Outstanding and
Collected cards and every bill's Total / Paid / Credited / Balance, each equal to
the hand-derived value, and each bill tying out (Total − Paid − Credited =
Balance). Most scenarios also tie out before the money moves.

## 2. The tiers — what each proves, and what it cannot

### L1 — offline (vitest; no network, no database, no Stripe)

```bash
npx vitest run --config tests/vitest.config.ts tests/e2e/runner-guards.test.ts tests/e2e/observe.test.ts tests/e2e/catalogue-sync.test.ts
```

- **Every runner guard, by behaviour**: refuses a tenant that is not northwind,
  live Stripe mode, a non-fixture rental, a sandbox call without
  `only_rental_id` (or naming another rental, or naming a real cron), an
  unconfirmed or un-previewed run, a forged or expired preview, a live webhook
  replay; preview's client cannot write.
- **By source**: the kill switch is the first decision; northwind is found by
  slug; the real cron is never called; Stripe is always the `"test"` client;
  every sandbox fire re-parks in `finally`; sim-control's staging-only 403 is
  untouched; the shift manifest and `sim_shift` / `e2e_shift_fixture` agree.
- **The catalogue's shape**: every branch present, every amount hand-derived
  and adding up, every live scenario ending in a tie-out, S1–S26 referenced
  exactly once.
- **The tie-out arithmetic** on hand-written rows, rule by rule (PAYG counts
  accruals not ledger rows, a Rental charge due tomorrow is not owed yet, a
  Refunded row is not collected, …).
- **Clone drift is pinned**: AE7 stays blocked exactly while the auto-extend
  clone lacks the real job's credit path.

*Cannot prove*: that any edge function, Stripe or the database behaves as the
catalogue says. That is the live tier.

### L1.5 — real Postgres, offline (PGlite)

```bash
npx vitest run --config tests/vitest.config.ts tests/e2e/dev-sim-runs.pglite.test.ts --testTimeout=240000
```

- The migration applies on the live schema fixture; its SQL guards refuse every
  non-fixture, non-northwind, live-mode or money-carrying rental; the shift
  moves only the fixture's columns; RLS lets northwind staff read, other
  tenants nothing, anon nothing; only `service_role` writes or executes.
- The catalogue's tie-outs for **SB1, MX1/MX2, AE1/AE4 and PP-L1** come out of
  the **live FIFO function bodies** exactly as hand-derived (PP-L1 by running
  the real plan engine's S1 on PGlite).

*Cannot prove*: edge functions, Stripe, webhooks, or the production schema's
drift from the Sep 25 fixture.

### Payment-plan engine scenarios (existing)

`npx vitest run --config tests/vitest.config.ts tests/payment-plans/scenarios`
and the Developer tab's **Payment plan simulator** — S1–S26 against the memory
store and PGlite. Referenced by PP-REF; not duplicated here.

### L2 — the live runner (Developer tab, northwind, Stripe TEST)

`supabase/functions/e2e-runner` + the Developer tab's live runner section
(built by the portal side, against `apps/portal/src/components/dev/e2e-runner-contract.ts`).

It creates a **flagged fixture** (an `E2E-FIXTURE …` customer at an
`@e2e.drive247.test` address with no phone, a rental marked
`creation_context.e2e_fixture`, no vehicle), mints Stripe TEST objects through
`sandbox-fixture-setup`, then runs the steps:

- **operator steps** call the same edge functions the portal calls, with *your*
  session: `charge-saved-card`, `process-refund`, `create-extension-checkout`,
  `payment-plan-manage`, `apply-payment`; where the portal writes rows from the
  browser (the Extend dialog's date patch and Extension charge, pause/resume,
  Add Payment) the runner writes exactly those rows;
- **time** moves by backdating only that fixture's driving columns
  (`e2e_shift_fixture`, sim_shift's contract);
- **cron work** runs through the `sandbox-*` clones with
  `only_rental_id` = the fixture — never jobs 6, 4, 32, 33, 54, 55 — or, for
  payment plans, the engine in-process scoped to the fixture's plan;
- **you** pay checkout links in a browser with `4242 4242 4242 4242`;
- after each check it reads every row hanging off the fixture and records the
  step, the rows and each assertion (expected / actual / pass, with the hand
  derivation) in `dev_sim_run_steps`.

*Proves*: the real paths, the real database, real Stripe TEST and the real
webhooks, end to end, for one rental at a time.
*Cannot prove*: live-mode Stripe (never used); the real cron **jobs** themselves
(the clones stand in — §6 lists where they have drifted); anything on a tenant
other than northwind; timing under genuine concurrency beyond two overlapping
calls.

### Tier 1 — local full stack (documented follow-up, not built)

Docker Supabase (`supabase start`) + `supabase functions serve` + Stripe test
mode through the Stripe CLI (`stripe listen --forward-to …/stripe-webhook-test`)
would let the same catalogue run with no production database at all, and let a
pay-link step be completed by `stripe trigger` instead of a person. **Needs**:
Docker on the dev machine and a Stripe **test** key (`sk_test_…`/`rk_test_…`,
never live) — roadmap §1 "needed from people". Same runner, pointed at the local
project, with the northwind guard satisfied by a seeded `northwind` tenant.

## 3. How you run it (Developer tab)

1. Open the portal on **northwind** → `/dev` → the live runner section. If it
   says a piece is missing (function not deployed, table not applied, switched
   off), nothing is clickable.
2. Pick a scenario (or a group) → **Preview**. This writes nothing. It lists,
   per scenario, every table a run will write, every Stripe TEST object it will
   create, and every sandbox job it will fire — and refuses to issue a preview
   id if northwind's settings differ from the ones the expected values assume
   (tax off, grace 48 h, …).
3. Confirm with the sentence shown ("This writes test rows to northwind in
   Stripe TEST mode") → **Run**. The page drives the run step by step.
4. When a step needs you, the run shows **the link and what to do**: open it,
   pay with `4242 4242 4242 4242`, any future expiry, any CVC, any ZIP, then
   press **Continue**. The runner waits up to 60 s for the webhook to land.
5. The run ends **passed** or **failed** with every assertion listed; reopen any
   past run later, and download its evidence as JSON.
6. **Close fixture** on a finished run switches its engines off and sets the
   rental Closed (money rows are left as evidence).

Terminal equivalent (the same function, the same checks):
`POST /functions/v1/e2e-runner` with your session — `{ "action": "preview",
"scenario_ids": ["SB1"] }`, then `{ "action": "run", "scenario_id": "SB1",
"preview_id": "…", "confirm": "This writes test rows to northwind in Stripe TEST mode" }`,
then `{ "action": "advance" | "continue", "run_id": "…" }`.

## 4. The guards (supabase/functions/e2e-runner/index.ts header)

| | guard | prevents |
|---|---|---|
| G0 | kill switch: nothing until `E2E_RUNNER_ENABLED=northwind` | a deploy doing anything |
| G1 | caller: a super admin, or northwind's head_admin (tenant by **slug**) | any other operator or tenant |
| G2 | tenant: northwind, active, `stripe_mode='test'`, on Stripe — every request, and again in SQL | a live-mode tenant; real customers |
| G3 | a Stripe **TEST** key; `SANDBOX_TEST_TENANT_ID` = northwind | live keys; clones locked elsewhere |
| G4 | scenario: live tier, not blocked, visa start, allow-listed cards/jobs, ≤ $1,000 steps, ≤ 60-day advances; assumptions hold | unlisted actions; wrong expected values |
| G5 | fixture only: registered by `e2e_register_fixture` (brand-new, marked, money-free, unreachable customer) — TS + SQL | touching a real rental; mail/SMS to a person |
| G6 | every sandbox call carries `only_rental_id` = fixture; its preview matches nothing else | a sandbox run widening |
| G7 | preview holds a read-only client; no run row | a dry run leaving rows |
| G8 | fixtures **parked** at rest (auto-extend off / PAYG paused / installment plan pending); un-parked only for one sandbox call, outside [−20 s, +90 s] of each real job's schedule | the real cron charging a fixture |
| G9 | time moves only via `e2e_shift_fixture`: fixture's columns, ≤ 60 days | backdating anything else |
| G10 | webhook replay only for the fixture's own TEST session | replaying anyone's money |
| G11 | one request per run (`e2e_lease_run`) | interleaved steps |
| G12 | confirm sentence + a fresh (15 min) HMAC preview id naming that scenario | a run nobody previewed and confirmed |

`sim-control` is untouched: still staging-only (403 on any other project). The
runner is its production counterpart for one tenant, with the set above.

## 5. What a run leaves behind

On northwind: the fixture customer and rental; their ledger, payment, extension,
accrual, installment and plan rows; P&L rows from FIFO; one `dev_sim_runs` row,
one `dev_sim_fixtures` row, one `dev_sim_run_steps` row per step. In Stripe
TEST: a customer, its test cards, a cancelled $1.00 hold, and the intents,
sessions and refunds the steps make. Fixture money shows in northwind's
Finances and P&L under the `E2E-FIXTURE` names — it is test data and says so.

## 6. Known limits — and what the runs are expected to expose

- **Clone drift.** The sandbox clones were cut from the real jobs weeks ago.
  `sandbox-auto-extend-rentals` lacks the real job's prepaid-credit and
  adjustment-credit path, so **AE7 is live-blocked** (a test pins it). The
  clones also predate other fixes (Square routing, the reconcile pass); a
  difference between a live run and production behaviour on those paths is the
  clone's, not the catalogue's.
- **Suspected defects** each named on its scenario (`suspect`), evidence decides:
  IN1 — installment payments are inserted `Applied`, which the FIFO trigger
  never allocates, so Outstanding may stay $600; CS1c — the renewal job claims
  nothing before charging, two overlapping runs may both renew; AE3 — SCA is
  retried blind and never sent a link; AE5b — the expired-session webhook may
  cancel the rental.
- **Finances rules are restated, not imported**: `observe.ts` restates the
  portal's balance / bills / receipts rules for one rental (the portal's files
  use `@/` imports the edge runtime cannot load). `observe.test.ts` pins them;
  change both together.
- **Stripe counts** come from the fixture's own Stripe customer — card-on-file
  charges only; a Checkout-paid link is counted from `payments` rows.
- **The auto-extend retry wait** ("next try in 16 h") is read against the
  moment the rows were read, rounded to the hour.

## 7. Before the first live run (approvals, not code)

1. Apply `supabase/migrations/20260926120300_dev_sim_runs.sql` (and the
   payment-plan migrations `20260925120000/120100/120200` for PP-L*/CS1a/CS2).
2. Deploy `e2e-runner`, `sandbox-fixture-setup` and the four sandbox clones it
   fires; `payment-plan-manage` for plan scenarios.
3. Set secrets: `E2E_RUNNER_ENABLED=northwind`, `SANDBOX_TEST_TENANT_ID=<northwind's id>`.
4. Check northwind: `stripe_mode='test'`, tax and service fee off, auto-extend
   grace 48 h / 3 retries, PAYG window 1 day — the Preview says which differ.

Tests, all offline: `npx vitest run --config tests/vitest.config.ts tests/e2e`.

# In-app human support (V2)

Repository implementation verified locally on 2026-09-15. Review candidate, not a deployment claim. New functions/migrations must be activated in an approved environment. No live email delivery or hosted account test is claimed.

## Operator workflow

Human support lives in the portal's own **Support** section (`/support`), not inside TRAX. The main sidebar's Support item (below Fines, with its unread-message badge) and TRAX's Open Support control both go there, so both entry points show the same authorized tickets; TRAX closes behind the navigation and keeps its AI conversation and unsent draft. Support is a three-area workspace, the same for the tenant and for platform support:

- LEFT — the tickets. On a desktop the sidebar BECOMES the Support rail on this route (as it becomes the conversation rail on `/trax`): Back to portal, Support and the tenant it is for, **New ticket**, a compact search and status filter, and the ticket rows — subject on up to two lines, the reference, the latest-message preview where the deployment provides one, the last-activity time and the status badge. Rows carry no leading dot, avatar or bullet: an unread ticket is stated by the subject's weight and the selected one by a lavender surface. The rail is 19rem on Support only; every other route keeps the normal navigation. If the sidebar is collapsed the page shows the list itself, and the collapsed rail offers Show tickets.
- CENTRE — the human conversation for the selected ticket: a compact header (subject, reference, status — no created/updated strip), chat bubbles sized to their content (the viewer's own on the right) grouped into turns under date separators, and the reply composer anchored at the bottom while the history scrolls on its own.
- RIGHT — **Details | TRAX Summary** for the same ticket. Details is a label-and-value list: reference, subject, status (read-only for a tenant; the working control for platform support), company, requester, whether it was opened from a TRAX escalation or the Support section, the TRAX topic, created, last activity, resolved, and the linked rental, vehicle, customer or payment references (the tenant's open the portal's own record pages). TRAX Summary shows what TRAX saved with the ticket when it was created: the reported problem, the checks TRAX ran and what they found, why TRAX passed it to support, what is still unresolved, and then the saved part of the tenant's TRAX conversation about that issue with the requester's own name and TRAX as the sender labels, and timestamps. It is read-only — there is no composer — and it is never regenerated when opened. A ticket opened directly in Support says "No TRAX conversation is linked to this ticket."; a handoff that kept no conversation says only the summary is available; and where the reader's current record permissions hide the context it says so rather than claiming there is none.

Selecting another ticket changes all three areas together, and nothing from the previous ticket is shown while the next one loads. Below 1280px the right-hand panel is a modal drawer opened from the conversation header's Details button (Escape and the scrim close it); below `md` the list and the conversation take turns, with Back.

THE TRAX MESSAGE IS AN EVENT. The automatic handoff posts its generated summary as the ticket's first message. The workspace draws that message as a one-line event — "TRAX created this ticket and shared its troubleshooting summary", with a link to TRAX Summary — never as a bubble that reads as if the requester or an agent wrote it. It is identified from stored metadata, not from its words: the server (`ticketSourceReader` in `support/messaging.ts`) marks a message when its nonce is the TRAX issue id on a ticket with a TRAX conversation behind it, which only the automatic handoff writes. A person's message that mentions TRAX stays that person's message. Nothing is deleted or rewritten: the stored text is still available under "Summary as posted to the ticket", and the event keeps its read marker so acknowledgement is unchanged. A deployment whose messaging function predates the marker shows the message as an ordinary bubble, as before.

Nothing in the interface interprets the word “resolved” in a message: a ticket's status is the one the server stores. The route is gated on the same `chrome` V2 rollout the endpoints enforce, and no tenant is sent to the platform (super-admin) inbox. AUTOMATIC HANDOFF. When the backend escalation policy takes an issue to its threshold, the server creates or reuses that issue's ticket in the same request as the answer — the requester does not retype the problem into a second composer. The first message on the ticket is a labelled TRAX troubleshooting summary (the question, the checks TRAX completed, why it could not close the issue, what is still unresolved and the records referenced), not a message attributed to a person. TRAX then states the real reference and offers **Open support ticket**, which opens that conversation in this section. An issue that already has a ticket is reported as already linked, and the SQL reuses it: no second ticket, no second first-message and no second email. A failure is reported as a failure with no reference, and the conversation offers a retry. Opening Support or the new-ticket composer still creates nothing; the tenant's own first Send does.

ATTACHMENTS. A message can carry up to three files — PNG, JPEG, WebP, GIF or PDF, 10 MB each — in both directions: the requester sends a screenshot, support sends one back. The file never travels through the support API. The client asks the server to reserve a path (`attach`), the database records it against the sender's identity and the message's nonce, and the browser uploads straight to a PRIVATE bucket with a one-time signed URL. The message that follows claims the uploads reserved under its nonce, so a retried send never stores the same file twice and an upload whose message never arrives stays out of the conversation (and is purged by `trax_support_attachment_purge`). Reading works the same way in reverse: the thread returns each file with a short-lived signed URL minted for that reader. SVG, archives and executables are refused, by both the client and the database's own check constraint.

Reply in the thread to continue. You and Drive247 Support identify the human participants; TRAX never posts a human reply. Support staff set Open, In progress or Resolved from the ticket's Details. Resolved maps to the existing `closed` database state. A tenant reply reopens that same ticket and clears its closure timestamp. AI suggestions and issue-resolution controls do not close a human ticket. New unrelated issues use New request.

The model is not involved in the support tickets view, reads, replies, unread counts or direct ticket creation. The escalation composer uses the existing authenticated issue handler only to copy its authorized context. During an AI outage the independent ticket composer remains available. Credentials, payment/card identifiers and obvious personal contact data are redacted before persistence. Human messages do not authorize rental, payment, insurance or other business writes.

## Platform support workspace

The actual platform app adds `/admin/support`, reached through Super Admin → Management → Support, immediately after Contact Requests. The navigation item is visible to platform super admins even when support storage is unconfigured or unreachable. Menu visibility is not ticket authorization. The page checks access before mounting the inbox, showing a specific local setup message, an access-required message, or an unavailable state with Check again. An unread badge appears only after a successful authorized count; failures never become a fabricated zero. `app_users.is_super_admin = true`, active membership, **and** an active explicit `trax_support_agents` grant are all required to read tickets or messages. Tenant admin roles, the email recipient, names/display labels and client `admin` flags confer no cross-tenant access. The older queue endpoints use this same platform restriction after the messaging migration.

On `/admin/support` the navigation sidebar is replaced by the platform Support rail (Back to dashboard, the queue, and the signed-in support identity); the navigation returns on every other admin route, and a phone keeps it behind the header's menu. The platform inbox (`shared/trax-support/SupportInbox.tsx`) and the tenant's section are both `shared/trax-support/support-workspace.tsx` over the same behaviour: `shared/trax-support/use-support-inbox.ts` holds polling, read-through acknowledgement, retry nonces and message ordering; `shared/trax-support/inbox-ui.tsx` holds the ticket list, row, status badge, bubbles and composer; `shared/trax-support/ticket-info.tsx` holds Details | TRAX Summary; and `shared/trax-support/support-rail.tsx` lets each page lend its one inbox to its app's rail. The two surfaces therefore read as one support system while their data access stays separate — a tenant reads only their own tickets, the platform queue only what its grant allows. The differences are the role's: the platform inbox searches companies as well as tickets ("Search tickets or company…"), names the company and requester in the conversation header, replies with "Reply to tenant…", and carries the status control in Details.

STATUS. The platform inbox's Details tab has a **Status** control with the three states the table actually stores: Open, In progress and Resolved (`closed`). Choosing one calls the existing authenticated `status` action, which commits the new status and a short note ("Support marked this ticket as In progress.") in one transaction; the SQL refuses it for anyone without the platform support grant, so this is not a frontend permission. The tenant's Support section reads that same ticket row — there is no second copy of a status — and its badge follows within the five-second reconciliation both inboxes already run, without a refresh or a sign-out. Nothing is claimed before persistence: the control shows "Saving…" while the request is in flight, and a failure leaves the stored status showing with an explicit error. Typing the word "resolved" in a message changes nothing. The inbox has search, existing-state filters, pagination, tenant/requester identity, last activity and unread markers. Select a ticket to see messages, reply and change status. Historical diagnostics are in the TRAX Summary tab. The handoff distinguishes user reports from timestamped observations. Current record permissions are rechecked for tenant access to this context; revoked diagnostic access hides the handoff without orphaning the owner's human conversation.

## Unread and updates

`trax_support_reads` stores a per-ticket, per-authenticated-viewer sequence.

TENANT BADGE — MESSAGES. The portal's main sidebar has a permanent **Support** item directly below Fines (it is no longer in the profile menu), opening the same `/support` section. Its badge is the number of unread MESSAGES from human support across the signed-in operator's own tickets: one reply is 1, two replies in one ticket are 2, and one more in another ticket makes 3; at zero, or while the number is not known, there is no badge. The row's accessible name carries it ("Support, 2 unread messages"). The server computes it on every `count` request (`unreadMessageReader` in `support/messaging.ts`, returned as `unreadMessages` beside the unchanged ticket-level `unread`): support-authored messages past that operator's own read-through, on tickets whose tenant and requester are the authenticated caller, after `trax_messaging_request('count')` has passed the same guard. It never counts the operator's own messages, TRAX's generated summary (stored on the requester's side) or a status change. STATUS NOTES are written by the server, not the client: the `status` action words the note itself and files it under a UUIDv8 nonce carrying a fixed `85a7` tag, derived from the caller's retry nonce so a retried change is still one message; the count excludes that tag. (Status notes written before this change are all already read, and read state only moves forward, so none can be counted.) Reading is unchanged and per viewer: opening Support marks nothing, and messages are marked read only when their conversation is open, the tab is visible and the message elements have been displayed — the other tickets' messages stay counted, and support reading a ticket records support's read state, never the requester's. The sidebar re-asks every 10 seconds while visible and at once on focus, reconnect, return to the tab and whenever a conversation acknowledges a read; a changed tenant, user or permission set, or signing out, resets it to unknown.

PER-TICKET BADGES. Every row in the ticket list — the tenant's Support section and the platform inbox alike — shows that ticket's unread INCOMING messages as a small solid-accent pill on the reference line, under the time, apart from the status badge; at zero there is none, and screen readers hear "2 unread messages" with the subject. Incoming depends on the viewer: for a requester, support-authored messages (never status notes); for platform support, requester-authored messages (never TRAX's generated summary, identified by the same stored rule as the conversation event; a ticket opened directly in Support still counts its first message, which is the requester's own words). Neither side ever counts its own messages or another agent's reply. The server adds `unreadMessages` to each row of every authorized `list` page (`ticketUnreadReader`), past that viewer's own read-through, so one administrator reading a ticket leaves every other administrator's counts alone. The requester's sidebar total and their rows come from the same function, so they cannot disagree, and the total spans every ticket rather than the page on screen. The subject is bold exactly when the row has a count. Loading the list, opening Support or fetching a thread marks nothing: a conversation is acknowledged only while it is open, the tab is visible, nothing covers it (reading pauses while the Details drawer is open) and its messages have been displayed; the list is then reloaded at once so that row's pill clears while the others keep theirs.

SENDER NAMES. The tenant side of a saved TRAX exchange is labelled with the person's own name, never the word “Tenant”, the company or whoever is reading. A TRAX conversation belongs to one signed-in user (`trax_support_conversations.user_id`, the ticket's `user_id`), so every tenant-side turn on a ticket is that person's; the name is the one the authenticated `detail` request already resolves for that user id (`participantName`), so each ticket resolves its own and switching tickets never carries a name across. The platform inbox labels the requester's messages in the human conversation the same way. A user record with no usable name — or one holding an email address — reads “Name unavailable” rather than inventing a name or exposing the address; nothing stored is rewritten.

PLATFORM BADGE — TICKETS. The admin navigation's count is unchanged: distinct tickets with incoming messages newer than that viewer's read position. Five unread messages on one ticket contribute one. An admin reading does not change another admin's badge. Own replies do not create incoming unread messages. Opening a list or fetching a thread never marks it read. The client acknowledges only displayed message elements, using the returned sequence rather than the current server maximum; a newer concurrent message stays unread.

The support tables deliberately have no direct browser SELECT/RPC grants or realtime payload subscriptions. Both apps automatically reconcile via the authenticated API (every five seconds for the platform badge and open inboxes, every ten for the tenant sidebar badge) while visible, and on focus, reconnect and visibility changes. No optimistic badge counter substitutes for persisted state. This is automatic polling, not WebSocket delivery. Requests time out and stop/reject late results when the account scope changes. A failed count is unknown, not a fabricated zero.

Messages are ordered by a per-ticket monotonic sequence, serialized under the ticket lock. Fetches return the latest 50 with older-message pagination; lists return 25 plus a next-page marker. Duplicate nonces cannot append twice. First-submission nonces survive refresh in session storage without storing message content there. Failed outgoing drafts remain in memory for retry; once a request is uncertain, Retry sends its original payload. Drafts are not promised to survive closing the page.

## Email alert and configuration

The existing approved `sendResendEmail` service is reused. No Gmail integration, mailto redirect or reply ingestion is added. `trax_support_email_jobs` is committed with the first tenant message and cascades only with ticket retention. Follow-ups update in-app unread state without adding new-ticket emails.

Server configuration:

| Setting | Purpose |
|---|---|
| `TRAX_SUPPORT_STORAGE=enabled` | Enable support storage after both migrations have been reviewed/applied in the chosen environment |
| `TRAX_SUPPORT_EMAILS=enabled` | Allow the deployed notification worker to deliver queued alerts |
| `TRAX_SUPPORT_NOTIFICATION_TO` | Requested destination defaults server-side to `ilyasghulam35@gmail.com`; use a test recipient in testing |
| `TRAX_SUPPORT_ADMIN_ORIGIN` | Actual platform admin origin; `/admin/support?ticket=<id>` is generated from it |
| `TRAX_SUPPORT_WORKER_SECRET` | Dedicated scheduler authorization, stored only in the server/Vault secret managers |
| `RESEND_API_KEY` | Existing transactional provider credential; not printed, shared with a model or sent to the client |

Attachments additionally need a PRIVATE storage bucket named `trax-support-attachments` in the same project, and the `20260917020000_trax_support_attachments.sql` migration. Create the bucket with public access OFF and no anonymous policies: every read and write is a short-lived signed URL minted by the server for a path the database reserved, so the bucket needs no policy of its own beyond the service role's. Until both exist, the attach control is not offered and the API answers "attachments are not configured" — messages still send.

The development apps use `/api/trax-messaging` with their existing server Supabase configuration; production uses the separately deployed `trax-messaging` edge function. The local route returns 404 outside development. No project URL, tenant or staff grant is hardcoded for production enrollment.

For local Next apps, configure each app's ignored `.env.local` (`apps/portal/.env.local` and `apps/admin/.env.local`) with the same intended project's `NEXT_PUBLIC_SUPABASE_URL`, browser `NEXT_PUBLIC_SUPABASE_ANON_KEY`, server-only `SUPABASE_SERVICE_ROLE_KEY`, and the storage flag. Restart those dev servers after changing environment settings. Never prefix the service key with `NEXT_PUBLIC_`. Platform support assignments use the approved staff member's `app_users.id` in `trax_support_agents.staff_id`, not their email or Auth user id. No grants or private environment files were changed by this implementation.

Deployment preparation: apply `20260915190000_trax_v2_support.sql`, then `20260915200000_trax_support_messaging.sql`, then `20260917020000_trax_support_attachments.sql` (and create the private bucket above); assign approved platform staff; deploy `trax-messaging`, updated `trax-support`, and `trax-support-notifications`; configure the settings above. Review `ops/trax-support-notification-schedule.sql` to schedule the worker every minute with pg_cron/pg_net and Vault-managed URL/secret. This script has not been executed here and contains no credentials. Provision the dedicated Vault entries privately before running it in an approved environment. This schedule does not enable retention deletion.

The worker leases at most five jobs per invocation. It freezes the rendered recipient/link/body before send, uses one stable provider idempotency key per ticket, records provider acceptance separately and retries failures with backoff (maximum eight attempts). An uncertain job older than 23 hours becomes `review`; it is not blindly resent beyond [Resend's documented 24-hour idempotency window](https://resend.com/docs/dashboard/emails/idempotency-keys). Simulated sends are failures for delivery accounting. Provider acceptance is not proof of inbox receipt. Administrator ticket details show pending, sending, failed and review states. Provider response text/credentials are not persisted in error messages. A provider failure never rolls back a ticket or its first message.

Alert template: `[Drive247 Support] New ticket #<reference> — <tenant>`, with tenant, requester display name, short subject, creation time, safe first-message preview and authenticated Open Support Ticket link. No diagnostic handoff or full transcript is emailed. Payment/identity-related previews are replaced with an instruction to inspect Support. Text is HTML escaped; links and lengthy identifiers in previews are removed. There is no authentication bypass in the email link.

## Permissions and storage contracts (developer reference)

`handleMessaging` accepts `action`, bounded action-specific `data`, optional tenant context hint and an admin-view flag. Server authentication derives user/staff identity; ordinary staff always use their membership tenant. The V2 rollout is rechecked with `authorize`. SQL rechecks active membership and the dedicated support grant in each transaction.

| Action | Input data | Output | Scope |
|---|---|---|---|
| count | none | unread distinct-ticket integer | Owner/current tenant or authorized platform queue |
| list | optional search ≤120, status, offset ≤10000 | 25 ticket summaries, nextOffset, unread | Same authorization, no cross-tenant owner results |
| create | nonce UUID, subject ≤240, body ≤4000 | Actual id/reference | Owner/current tenant; 10 new tickets/hour |
| detail | ticket id, optional before sequence | Ticket/handoff, up to 50 ordered messages, hasOlder/latestSeq | Revalidate ticket access and diagnostic context |
| send | ticket id, nonce UUID, body ≤4000 | Persisted message and sequence | Owner or authorized platform staff; 30 messages/minute |
| read | ticket id, displayed through sequence | Confirmed read position | Current viewer only; monotonic, cannot exceed server sequence |
| status | ticket id, nonce UUID, body, existing status | Confirmed status | Platform support only; status and human update atomic |

There are no arbitrary SQL/HTTP/model mutation tools. Private tables are service-only with RLS enabled and no browser grants. Missing/inaccessible tickets return the same unavailable access result. Messages are plain text, not executable instructions or trusted markup. Neither shared knowledge nor the AI receives ticket threads by default.

Retention remains 90 days after ordinary AI-chat activity, open human tickets retained, and closed tickets 365 days after their latest closure; reopening cancels deletion. Ticket messages, read positions and email jobs cascade with the retained ticket. Copied redacted handoffs survive ordinary AI-chat cleanup. Approved holds and configurable administrator policy remain. Destructive production cleanup is still disabled pending approval. Provider/backup retention remains separately governed as described in support-escalation.md.

Run `node tests/trax/messaging-storage.mjs` for actual isolated PostgreSQL migrations, `node tests/trax/messaging-browser.mjs` for rendered tenant/admin flows using the real handler and isolated database, and the portal's `trax-messaging.test.ts` / `trax-escalation.test.ts` regressions.

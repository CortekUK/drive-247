0 · How to read this document

This is not a wish-list. Every claim below was checked against the live production database and the actual repository. Where the popular assumption is wrong, it says so. Where a number is inflated by demo data, the real number is given.

The single most important finding is this: Drive247 already contains roughly 60% of a maintenance system. It is scattered, partly orphaned, partly broken, and entirely un-surfaced — but it exists. The work is far less about building new machinery than about connecting, repairing and exposing what is already there. Building a fresh "maintenance module" alongside it would create a second, competing source of truth for cost and availability, and would actively make the product worse.

1 · Verdict & strategy

Brandon is right that maintenance is the correct next feature, and right about why: it is the only thing that gives an operator a reason to open Drive247 on a day with no bookings. But the version described in his message — health scores, work orders, parts/labour, predictive maintenance, telematics — is a Fleetio clone that would take months and would land on a data substrate that cannot support it.

The blocking constraint Mileage-interval maintenance ("oil change every 5,000 miles") is the centrepiece of the proposal. Across the entire production database, exactly 5 vehicles have both a current odometer reading and a last-service mileage. Of 196 real vehicles, 40 have any odometer reading at all and 10 have a last-service date. There is no UI anywhere in the product that lets a human type a starting odometer — the only writer is the key-handover screen. A mileage-based feature therefore has almost nothing to compute against on day one, and no way for an operator to fix that.

The strategy that follows from that

Invert Brandon's ordering. He proposed schedules first and compliance later. The data says the opposite:

  1. Lead with legal compliance, not servicing. Registration/inspection dates are the best-populated maintenance data in the system and the highest-liability gap. Renting out a vehicle whose inspection has lapsed is a strict-liability offence for the operator and typically voids their own motor policy. Today nothing in the product reads those dates for availability — a vehicle with an expired inspection is fully bookable and publicly listed. That is both the strongest adoption hook ("this stops you renting an illegal car") and the most defensible reason to build.
  2. Make the odometer capturable before making it computable. Every mileage rule is blocked on a capture path that does not exist. Fix capture first; intervals become possible as a consequence.
  3. Make the maintenance hold real. The promise "automatically take unsafe vehicles out of availability" is currently unenforceable — see §5.1. Until a hold cannot be bypassed, every downstream feature is decorative.
  4. Design for one person, not a team. 17 of the 23 vehicle-owning tenants have exactly one staff login. There are 4 manager users and 2 ops users on the entire platform against 47 head_admins. Every "assign it to ops / the manager reviews it" workflow is fiction.
Positioning Brandon's instinct to avoid calling it "vehicle maintenance management" is correct, and there is a technical reason to insist on it: the word "maintenance" is already taken three times in this codebase (§5.9). Fleet Health is the recommended name for the product surface, and every new database object should be namespaced vehicle_* to avoid colliding with the existing tenant-health and platform-maintenance systems.

3 · What already exists

Reusable today. Building parallel versions of any of these is the main risk to the project.

3.1 The service + cost spine works well

service_records is already the canonical completed-work log, and it is wired far better than anyone expects. A single trigger does three jobs:

  • update_vehicle_last_service() re-derives vehicles.last_service_date and last_service_mileage from the newest record.
  • upsert_service_pnl_entry() writes a pnl_entries Cost/Service row keyed reference='service:<id>' — an idempotent upsert, correctly deleted on removal.
  • Deletion cleans both up.
Architectural consequence A completed maintenance job must settle into service_records. Do that, and P&L posting, the service baseline and the vehicle's last-service fields all update for free, idempotently. This is the single cleanest decision in the whole design — and the reason a separate maintenance_costs table must never be created.

3.2 The availability + hold mechanism exists but broken

A Maintenance vehicle status and an auto-release reconciler already exist and are live:

  • vehicles.status = 'Maintenance' + a blocked_dates row covering today = "off the road".
  • Cron job 56 (0 1 * * *) runs sync_vehicle_maintenance_status(), returning the vehicle to Available/Rented once no block covers today.
  • VehicleStatusBadge already renders Maintenance with a wrench and amber styling — zero UI work needed.

Caveat: no vehicle has ever held this status, the only writer is swap_rental_vehicle, there is no UI to set it, and the reconciler has several defects (§5.1–5.3).

3.3 The reminder engine works, but not the way it looks

reminders is a generic polymorphic table (rule_code, object_type, object_id, due_on, remind_on, severity, status, snooze_until, context) and vehicle-scoped reminders already exist and fire: MOT_30D, MOT_7D, MOT_0D, TAX_30D, TAX_7D.

Do not use the rule engine The "designed" pipeline (reminder_rules → reminders-generate → process-reminders) is dead: reminder_rules has 0 rows, so the generator early-returns before reaching its vehicle loop; none of those six edge functions has a cron job; and the one reminder cron that does exist posts to a foreign Supabase project. Every alert that actually works in production is hand-rolled — code that learns a fact writes a reminders row directly with its own dedupe guard. Follow the working pattern, not the designed one.

5 · Defects that must be fixed first

Each of these breaks a promise Fleet Health would make. They are ordered by severity.

5.1 A maintenance hold is bypassable blocker

The DB trigger check_rental_overlap() is the only server-side booking guard, and it compares rentals to rentals only. It never reads blocked_dates and never reads vehicles.status. Every block check in the product is a client-side SELECT before an INSERT, duplicated across at least 8 call sites in booking and portal, with no transaction and no lock. Zero of the ~300 edge functions reference blocked_dates.

Worse, the portal's own manual booking form deliberately ignores vehicle-specific blocks (rentals/new/page.tsx:482 — "Admin portal only enforces global blocks"), which covers 199 of the 203 live block rows. That is the widest bypass and it is on the screen operators use most.

Required Add a second EXISTS clause to check_rental_overlap against blocked_dates, raising a distinct error code so the UI can say "in service" rather than "double-booked". It must respect the function's existing check_start fast-path variable — the live function sets check_start := OLD.end_date on a pure extension, and ignoring that would make every auto-extend fail on any vehicle with a historical block. Also specify what auto-extend-rentals does when it now hits this exception mid money-flow: it must pause with a reason, not die inside a ledger write.

5.2 Every hold releases hours early blocker

The database runs in UTC and cron 56 fires at 0 1 * * * UTC. Every tenant timezone is behind UTC (America/New_York 31, America/Chicago 8, America/Los_Angeles 4, America/Denver 3). When the reconciler evaluates end_date >= CURRENT_DATE, the UTC date has already rolled while it is still 18:00–21:00 the previous day locally.

So on the final day of every maintenance window, for every tenant, the vehicle flips to Available 3–7 hours early — while the client-side block checks still consider the day blocked. Status and blocked_dates disagree, and during that window the portal booking form will rent the car with no friction at all.

5.3 The reconciler is unsafe as written blocker

sync_vehicle_maintenance_status() is an unconditional bulk UPDATE with no tenant filter, no is_disposed guard, and no awareness of whether work is still open. It competes with three TypeScript rental-close paths, at least four edge functions, and three SQL functions (dispose_vehicle, undo_vehicle_disposal, swap_rental_vehicle) — none of which read the current value before writing, seven of which set Available unconditionally. There is no status history and no audit of the prior value, so a wrong state is undiagnosable.

Related: blocked_dates has 59 overlapping pairs live and no unique or exclusion constraint. "Is this vehicle off the road" is a range-union question, not a row lookup — so completing one job and deleting its block may leave the car stuck in Maintenance behind a second block, with no UI explaining why.

5.4 Odometer capture is unguarded blocker

use-key-handover.ts:604 is the only writer of vehicles.current_mileage in the repo, and it:

  • guards with if (mileage) — so a legitimate 0 on a brand-new vehicle is falsy and silently skips both the vehicle write and the excess-mileage calculation;
  • writes on both giving and receiving with no monotonic guard, so readings can go backwards (one vehicle is already below its own highest recorded reading);
  • has no tenant predicate on the vehicles UPDATE;
  • is optional — a "Continue Without Reading" dialog waives it, and 51 of 160 handovers have no reading.

Separately, update_vehicle_last_service() takes the newest record regardless of service_type, and NULLs last_service_mileage when the newest record has no mileage. So a quick "brakes, £340" entry with no odometer permanently destroys that vehicle's interval baseline. It must COALESCE to the newest non-NULL mileage.

5.5 Mid-rental swaps corrupt mileage attribution armed today

rental_key_handovers has no vehicle_id column and is UNIQUE on (rental_id, handover_type) — so it structurally cannot record which physical car a reading belongs to, nor more than two readings. One live rental has been swapped twice, meaning three vehicles on one rental.

Four live rentals currently have a giving reading recorded before a swap and no return reading yet. The moment a return odometer is typed, the delta spans two physical vehicles and the reading is stamped onto whichever car happens to be attached. This is armed, not theoretical.

5.7 Compliance is modelled in the wrong jurisdiction decision needed

The only compliance fields are mot_due_date and tax_due_date — UK vocabulary. But all 46 tenants are USD, tax rates are US state sales-tax shaped, and tenant names are LLCs. There is no country or state column on tenants (only a free-text address), and vehicles.garaging_state is populated on 204 vehicles all belonging to the demo tenant and zero real ones.

MOT is one national annual test. US state inspection is not: New York is annual safety + emissions, Texas annual, California biennial smog with model-year exemptions, Florida has none — and registration renewal is a separate obligation on a separate cadence. A feature keyed on mot_due_date tells a Florida operator to book a test that does not exist.

5.8 The evidence chain will not survive a dispute blocker for any charge

  • Handover photos live in a public bucket with policies granting every authenticated user SELECT, UPDATE and DELETE — including the renter being charged, who authenticates against the same Supabase project.
  • handed_by is NULL on all 160 handovers; uploaded_by is NULL on all 1,119 photos. There is no named custodian for any evidence.
  • detect-vehicle-damage upserts and wipes reviewer_notes/reviewed_by on every re-run, and its findings reference photos by positional index into a mutable list.
  • Client-side upload rejects files over 10MB or non-image/* by silently returning — no toast, no error. That is exactly what a modern iPhone produces, and the staff member walks away believing the photos uploaded.

5.10 Isolation and realtime hazards

  • RLS is disabled on 72 public tables, including every table Fleet Health touches: vehicles, service_records, vehicle_events, blocked_dates, rental_key_handovers, reminders. Isolation currently depends entirely on a hand-written .eq('tenant_id', …) in each hook.
  • blocked_dates is in the realtime publication with RLS off. A free-text reason like "engine warning light" or a garage name is broadcast to any holder of the public anon key — which ships in the booking bundle. Keep narrative text off blocked_dates; store a structured reason_code there and the detail on the tenant-scoped table.
  • use-calendar-blocks.ts deletes blocks by id with no tenant predicate — a safety hold is cross-tenant deletable.
  • vehicles is not in the realtime publication, so a status flip propagates to nobody. It must not be added while RLS is off — that would broadcast every tenant's fleet. Follow the documented tenant_subscriptions pattern instead: touch a published row, re-read over authenticated PostgREST.
  • Route protection fails open: any route absent from ROUTE_TO_TAB is reachable by every manager. Two edge functions carry hardcoded ALLOWED_TAB_KEYS lists already 10 keys behind permissions.ts.
  • vehicle_events has tenant_id NULL on all 84 rows, so its hook returns zero rows for everyone. Needs a writer fix plus backfill before the timeline works.

6 · Core architecture

6.1 Five principles

  1. Observation, not state. Mileage is a stream of dated, attributed observations. vehicles.current_mileage becomes a derived cache (MAX over observations), never a last-writer-wins scalar.
  2. One settlement path. Completed work settles into service_records. P&L, baseline and last-service fields follow automatically. No parallel cost table.
  3. One transition authority. A single SECURITY DEFINER RPC is the sole writer of vehicles.status, modelled on swap_rental_vehicle, writing an audit row on every transition.
  4. Unknown is a first-class state. Distinct from "not due", counted and surfaced. On day one it is the majority.
  5. Enforce at the database. Any rule the product promises to enforce lives in check_rental_overlap, not in a client filter. Client checks are advisory UX only.

6.2 The evaluation model

Health status is computed by cron, cached on a row, and recomputed on specific triggers. Compute-on-read is too expensive for a fleet list; compute-on-write misses the pure clock events (a due date passing changes nothing in the database).

Recompute triggers — the complete set
  1. A handover mileage write (either direction)
  2. A manual odometer correction
  3. service_records insert / update / delete
  4. A maintenance schedule created, edited or deleted
  5. A vehicle swap on an open rental
  6. A compliance date edited on the vehicle
  7. The nightly sweep — the backstop, and the only thing that can catch a due date simply passing

6.4 Forecasting

Brandon's "service expected in ~12 days" converts a mileage gap into a date, so it can flow into the existing date-based reminder table:

projected_date = today + (miles_remaining ÷ daily_burn)

daily_burn resolves in priority order: (1) this vehicle's own observed burn between its last two readings; (2) the tenant's fleet median; (3) the platform median (166 mi/day, p90 320, from the 25 rentals with both readings). Where future bookings exist, add their estimated mileage to detect a breach during a booking. Always show the confidence tier — an estimate from platform median is not the same claim as one from two real readings on that car.

Excluded from any burn calculation: rentals with a swap (the delta spans vehicles), readings older than 180 days, and any vehicle whose readings regress.

8 · The end-to-end flows

F1 · Establish the baseline gating requirement

Nothing works without this, and it is the flow most likely to be skipped.

First run, per tenant
  1. Operator enables Fleet Health in Settings (per-tenant flag, default off).
  2. System computes coverage. If below threshold it renders a setup screen, never an all-unknown table.
  3. Setup walks the vehicle list ordered by urgency — highest utilisation, oldest last-service, soonest compliance date — asking only for: odometer today, last service date, last service mileage. Three fields.
  4. Progress is explicit and finite: "7 of 22 vehicles set up".
  5. Compliance dates already present (~38 vehicles) light up immediately with zero input — the tenant sees value before finishing setup.
  6. CSV import offered for tenants coming off a spreadsheet.
  7. Pre-existing overdue items seed as acknowledged/historical at reduced severity with a distinct rule code — see the backfill warning below.
Backfill blast radius Across real vehicles, 25 already have a past registration date and 19 a past tax date. Switching generation on emits ~44 immediate criticals across a 173-vehicle fleet — a quarter of every real car alarming at once — then near silence. Combined with send-reminder-notifications having no tenant filter on either its reminders query or its app_users query (a verified cross-tenant fan-out), an unguarded first run is an incident, not a launch. Require per-tenant opt-in before first generation, cap alerts per tenant per run, and fix the tenant scoping before routing anything new through it.

F2 · Configure a schedule

Opt-in, never a prerequisite
  1. Tenant-level defaults may be set once (oil 5,000 mi / 6 mo, tyres 7,500 mi, brakes 10,000 mi, etc.).
  2. Any vehicle may override or exclude a rule.
  3. Rules are strictly optional. With zero configuration the product still surfaces compliance dates and last-service age — 12 of 23 tenants have ≤4 vehicles and will never configure intervals.
  4. Mileage rules on a vehicle with no anchor render as Unknown with a one-tap "add a reading" action — not as "not due".

F3 · Odometer intake

Four sources, one stream
  1. Handover (primary today). Fix the if (mileage) zero bug, add vehicle_id, populate handed_by, add a plausibility check against the last reading with an explicit override, and prefill from the vehicle's current value.
  2. Manual entry new, gating — an audited control on the vehicle page. This is the only way to seed a fleet or correct a bad value, and it does not exist today.
  3. Customer-reported decision D4 — a link in existing rental reminders to a simple authenticated page. Marked source='customer', unverified. This is the only viable source for a 90-day rental or a lockbox tenant.
  4. Telematics — deferred; the Tesla integration is dead in production and never read odometer anyway.

Write rule: the vehicle cache updates via GREATEST(COALESCE(current_mileage,0), new_reading) in a DB trigger with a tenant predicate. Corrections go through an explicit audited action that records the prior value and a reason.

F4 · Evaluation & forecast

Nightly sweep + trigger recompute
  1. Resolve each active rule's anchor: last matching service_records row by service_type — never vehicles.last_service_date, which is "last any service" and cannot drive per-item intervals.
  2. Compute remaining miles and remaining days.
  3. Convert miles remaining into a projected date using §6.4, tagging the confidence tier.
  4. Overlay confirmed future bookings and their estimated mileage; flag a projected breach during a specific booking.
  5. Write the derived status and reasons to vehicle_health_cache.
  6. Raise or resolve reminders rows against the ordinal key from §7.

F5 · Alerting

Alert fatigue is the measured current state, not a future risk 99.1% of 14,448 notifications are unread. Snooze has never been used once across 598 reminders. Only 6 of 39 tenants have operator email enabled and only 4 have a recipient address — so the email path can reach at most 4 operators. There is no staff phone number column on app_users at all, and all SMS/WhatsApp plumbing is wired exclusively to customers. There is currently no channel that can reach a human about a maintenance event.

Recommendation: ship Fleet Health alerting as pull-first and say so plainly. A persistent count on the Vehicles nav item and amber/red rows in lists the operator already opens will outperform pushing into a 14,000-deep unread pile. Set an explicit per-tenant weekly alert budget and define what happens at the cap. If push is wanted later, it needs new infrastructure (a per-user contact number, a staff notification transport) — that is a scoped project, not a checkbox.

F6 · Taking a vehicle off the road the critical flow

Scheduling a hold
  1. Operator picks a window. The system proposes the best gap from the existing calendar data — Brandon's "Suggested slot: Tuesday, no bookings".
  2. Conflict check runs against ['Active','Pending']. Today blocked-dates-manager.tsx checks ['Active','Confirmed'] — and "Confirmed" does not exist in live data while "Pending" (25 live rentals) is never checked. That is a real bug on the current screen.
  3. Conflicts are shown with the amount already paid, and each must be resolved before the hold commits: swap, reschedule, or refund.
  4. The hold commits inside a single SECURITY DEFINER RPC modelled on swap_rental_vehicle — job row, blocked_dates row and status transition in one transaction.
  5. The block carries a structured reason_code only. Narrative stays on the tenant-scoped job table (blocked_dates is broadcast with RLS off).
  6. Release happens when the job completes, not merely when the calendar window ends — and only if no other block still covers the vehicle.
Taking an actively-rented vehicle off the road There is no mechanism for this on a fixed-term rental. payg_paused exists and is respected, but only 1 of 73 open rentals is PAYG. The other 72 have no pause, no pro-rata credit and no substitution clause in the agreement — the three refund functions are all cancellation-shaped. Recommendation for v1: refuse to take an actively-rented vehicle off the road and force the swap_rental_vehicle flow instead, which at least reassigns the customer to a car. A PAYG hold should set payg_paused — the agreement already promises this and nothing implements it.

F7 · Doing the work

Deliberately thin in v1
  1. A job carries priority, category, status, and free-text notes.
  2. The garage is picked from a reusable vendor list (P2) rather than retyped — the current free-text vendor field is why the data is unusable.
  3. "At the garage — expected back <date>" is a valid state that does not require knowing what work is being done. This is the realistic small-operator case.
  4. An invoice is captured as a photo of paper into a private bucket. No parts/labour split in v1.
  5. Anyone opening or acting on a job stamps acknowledged_by, visible to everyone else — cheap prevention for the two-staff-both-book-the-garage case.

F8 · Completion & settlement

The one path that must not be duplicated
  1. Operator marks the job complete, entering date (defaulted to today), odometer (prefilled, one tap) and cost.
  2. The system writes one service_records row and stores its id on the job.
  3. Existing triggers then fire automatically: P&L posts idempotently as service:<id>, and the vehicle's last-service fields re-derive. No new cost-posting code is written.
  4. The odometer entered also lands as an observation, resetting the mileage baseline for that rule.
  5. The job's own block is released; if another block still covers the vehicle, it stays off road and the UI says which one is holding it.
  6. The matching rule's next due is recomputed and its reminder resolved against the max ordinal.
Double-count guard — required If the operator also logs the garage invoice as a vehicle_expenses row categorised Service, the cost doubles across every P&L surface, invisibly. Required: a nullable FK from vehicle_expenses to the job, and handle_vehicle_expense_pnl must skip its P&L insert when that FK is set. Ship a same-vehicle / ±7-day / similar-amount duplicate warning — it returns zero rows today, so it stays cheap.

Also: upsert_service_pnl_entry hardcodes category='Service' and ignores expense_categories entirely, while the expense trigger respects pnl_bucket. One tenant maps Service to a different bucket, so their maintenance spend splits across two P&L categories depending on which table it was entered in — and it will never reproduce in dev.

F9 · Return inspection → defect

Activating what is already built
  1. At receiving handover, staff complete a short checklist alongside the odometer: tyres, warning lights, brakes, glass, body, interior, cleanliness.
  2. Photos capture with capture="environment" so the camera opens directly, downscaled client-side before upload, with a visible per-photo state (queued / uploading / failed / retry). Today an oversized iPhone photo fails silently.
  3. Outcome: Pass · Attention · Off road.
  4. "Attention" or worse creates a vehicle_maintenance_jobs row linked to the rental — Brandon's "Issue #2041 reported after Rental #3842".
  5. A critical defect proposes an immediate hold, which runs F6's conflict check.
  6. The gate must be deferrable. A car returned at 19:00 on a Saturday cannot block deposit release until Monday — the Stripe authorisation has an expiry clock running. Default to "flag now in two taps, detail later" with a visible "awaiting inspection" state bounded by deposit_hold_expires_at.
Lockbox tenants 9 tenants have lockbox handover enabled, where nobody is present at either end. A handover-only inspection design degrades to zero coverage for them, and the product's own direction is toward more self-service. Their only viable paths are a customer-facing prompt (F3 step 3) or a periodic staff "yard walk" capture independent of any rental. This must be stated explicitly rather than assumed away.

F10 · Damage → renter recharge

Only after §5.8 is fixed. Preconditions, all of them: bucket made private with signed URLs; handed_by/uploaded_by populated; damage reports made append-only with a version once a charge references them; and the evidence bundle frozen at charge time — resolved URLs, content hashes, finding text, model, timestamp and named actor snapshotted onto the charge.

Money then flows through the existing paths (apply-fine or capture-deposit-hold). Note that neither applies sales tax, and 16 tenants have tax enabled at 3–13% — §12 D5.

F11 · Where the signal actually appears highest leverage, lowest cost

A solo operator will not open a Fleet Health tab. They open Rentals → New, pick a car, and hand over keys. If "inspection expired 4 days ago" is only visible on a tab they never open, the feature changes no behaviour even with perfect data.

Inline chips wherever a vehicle is chosen
  1. The rentals/new vehicle picker — the single highest-value placement.
  2. The swap-candidate list — which already renders a "Blocked for maintenance" badge, so the pattern exists to copy.
  3. The vehicles list row and the fleet calendar.
  4. Each placement declares whether it warns or blocks. A warning an operator can override with a reason will be adopted; a hard block on a car they need to rent today will be worked around or will kill the feature.

F12 · Reporting

Ship cost: maintenance spend per vehicle, per category, over time; cost per mile where mileage exists; days off road. Withhold ratios — maintenance-to-revenue and any disposal recommendation — until §5.6 is resolved. Also fix get-vehicle-profitability, which silently treats "all time" as the last 365 days, and which cannot distinguish "in the shop" from "idle" in its utilisation denominator.

F13 · Trax AI

Cheaper than expected — one SQL function
  1. Extend get_rag_metrics(p_tenant_id) with maintenance aggregates. This is the channel Trax actually answers counting questions from, and it is injected into the prompt as authoritative.
  2. Do not rely on the vector store: 80,565 sync rows are unprocessed, rag-sync has no cron and no caller, and the corpus is a frozen five-month-old snapshot covering 58 of 452 vehicles.
  3. Optionally add a schedule_maintenance action to the existing propose→confirm→execute registry (which currently holds exactly one action).
  4. Insight cards ("this vehicle is 186% above your fleet average") follow the generate-review-summary pattern — but must be phrased as cost observations, not disposal advice, until §5.6 is fixed.

10 · Non-functional requirements

10.1 The interaction budget treat as a requirement

This is the most likely cause of abandonment and it is measurable, not speculative. To log one service today an operator must open the portal on a phone, load a 1,673-line client page, scroll past twelve unrelated cards, open a dialog, and type a date, a type from 14 options, a mileage they do not have, and a cost. Recording an odometer means loading a 7,756-line page. There is no PWA (no manifest, no service worker), no camera capture attribute anywhere in the portal, and no offline buffer. The evidence that this already fails: 41 service records across 8 tenants, 27 of them from a single tenant.

Budget Logging a completed service or an odometer reading must be ≤3 taps from the portal home on a phone, must not require loading either mega-page, and must work one-handed. That implies a global "quick log" entry point (vehicle picker → number pad → done). Cost the lightweight route as part of the feature, not as a follow-up.

10.2 Form friction is currently inverted

service_type is required with 14 fixed options while mileage is optional — exactly backwards. Mileage is the field with downstream consequences; type is the field operators cannot be bothered with. The live data proves it: 22 of 41 records are typed "Other"/NULL and 21 have no mileage. Default the date to today, make type optional with a free-text fallback, and push hardest on mileage (prefilled, one tap to confirm).

10.3 Data retention

1,119 condition photos already sit in a world-readable bucket with no TTL, and zero cron jobs delete anything. The privacy policy contains no reference to photos, images or retention. Adding maintenance photography multiplies an already-undisclosed indefinite retention of imagery containing plates, locations and bystanders — and silently defeats the existing hide_vehicle_registration feature. A retention period tied to the dispute window, the mechanism that enforces it, and the disclosing policy sentence are all in scope.

10.4 Never certify safety

The product must not output a binary "safe" state. Model it as "inspection recorded by <named user> at <time> against <checklist version>", with the checklist stored immutably and explicit portal copy that this is an operational log, not a roadworthiness certification. Require an actor id on every inspection record from day one — it is unbackfillable, as the 1,279 existing actor-less rows demonstrate. The rental agreement contains no roadworthiness warranty and no disclaimer, so a Fleet Health screen would be the closest thing to a safety representation this product has ever made.

10.5 Conventions to follow

  • React Query keys include tenant: ["vehicle-health", tenant?.id, …], with enabled: !!tenant.
  • Follow use-expenses.ts for the CRUD + storage + DEPENDENT_KEYS invalidation fan-out pattern; vehicle-owners for page anatomy; reminders for stats + filters + bulk actions.
  • Schema changes via mcp__supabase__apply_migration, never hand-written files — the repo has 69 files with no live row and 43 live rows with no file, so db push would replay DDL that already exists.
  • Regenerate types and copy to all four apps (portal, booking, admin, bonzah).
  • Tests are pure-logic Vitest only — nothing renders, because portal pins React 18 while the root hoists React 19.
  • Design tokens: indigo #6366f1 accent, #eef2ff table headers, 1px #f1f5f9 borders, no shadows, DM Sans.

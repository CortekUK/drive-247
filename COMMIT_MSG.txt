feat(square): close the correlation, refund-safety and retry defects

Square could take a payment and never record it, report refunds that were
never issued, and turn a double-click into a double allocation. All three
are closed, plus the background jobs Square needs that Stripe does not.

CORRELATION - payments were taken and lost
The adapter returned a `persist: { square_order_id }` block documented as
"the caller's obligation". No caller honoured it, so nothing wrote
square_order_id and square-webhook could never match a row: the buyer paid,
the webhook logged "no local payments row" and returned 200, and Square
stopped retrying. Persistence moved INTO the seam: the payments row is
inserted BEFORE Square is called, and a failed insert aborts rather than
returning a payable URL we cannot track.

REFUND SAFETY - refunds reported as done that never happened
skip() is handled:true with NO error flag. Four of five refund callers
tested only .error and took the success branch, so a deactivated connection
or a missed webhook produced "refunded" while nothing left Square -
deduct-from-deposit even incremented refund_amount for a deduction the
processor never made. All five now branch on .skipped.

RETRY - one collection allocated twice
The Square idempotency key is deterministic but the row insert was not, so
a second "Pay" click produced ONE link and TWO rows sharing an order_id.
square-webhook completed the newer; recover-pending-square-payments then
found the older, saw the order genuinely PAID, and allocated it again. The
row now carries the idempotency key under a unique index and a retry adopts
the existing row. A settled row refuses a second link outright.

Also: per-attempt refund identity (two equal partial refunds no longer
collapse into one at Square), an uncorrelatable link is now revoked
automatically instead of asking an operator to void it by hand, and a dead
attempt releases its key so a transient error cannot permanently block a
collection.

Background jobs (migration written, NOT yet applied): Square OAuth tokens
expire in 30 days and the token IS the merchant addressing, so
refresh-square-tokens is a launch blocker with no Stripe analogue. Schedule
it only after the Square functions are deployed.

STRIPE IS UNTOUCHED. Stripe webhooks, _shared/stripe-client.ts and every
subscription function show zero diff; platform billing stays Stripe-only.
The Stripe money functions gain a preamble and one widened select. All 52
tenants remain on Stripe and both provider columns default to 'stripe'.

Verified: 978 tests pass (39 files, +27). Each new test was mutation-tested
- reverting a fix turns a specific test red. The first version of the
refund suite passed while the bug was fully restored, because it matched
".skipped" in an error message rather than in the guard; it now inspects
only branch conditions. Portal types 146 (baseline 147), admin 0, all five
apps build.

Note: process-refund's Square branch was reconstructed after a git checkout
during mutation testing discarded it. Worth a targeted review.
